# Astra (Codex gpt-6-astra) architecture note, 2026-09-06

Written in answer to: "are there large-scale architectural changes that would resolve whole classes of the 501 coverage findings?" Snapshot reviewed: bfcec9fd. Companion to `review-campaign-2026-09.md`.

Yes. I would change a few ownership and persistence boundaries now, while continuing the smaller fixes by family. The repeated failures come from several layers independently deciding whether the same operation was accepted, delivered, cancelled, persisted, or obsolete. A shared promise wrapper or another JSON helper cannot settle those disagreements.

I used the 501 entries in [the coverage audit](cover/astra-findings.md), the [family grouping](cover/families.json), and the surrounding implementation, with bfcec9fd as the main code snapshot. The audit has 343 app, 142 daemon and 16 relay findings. The grouping contains 399 distinct entries, leaving 102 ungrouped; its largest categories include 98 late/stale results, 57 unhandled asynchronous failures, and 54 premature or false success reports. Those categories are symptoms, so I have not treated their totals as the number a particular framework would fix. Authentication, tunnel and gate implementation are outside this analysis.

The estimates below concern findings in that historical audit, including some already repaired. They are not counts of currently open GitHub issues. They estimate failures prevented after the described migration, rather than everything that becomes easier to debug. Some contracts reinforce one another, so the ranges should not be added. Costs are my planning estimates for one engineer familiar with Joy, including migration and meaningful regression checks, but excluding a replacement terminal UI.

| Rank | Architectural change and what it replaces | Approximate direct findings | Cost and main risk | My decision |
| --- | --- | ---: | --- | --- |
| 1 | Transactional command/event ledger replaces independent queue, receipt, checkpoint and spool writes | 25–35 | 4–7 engineer-weeks; migration mistakes can lose accepted work | Start now with acceptance and outbound delivery |
| 2 | One daemon session coordinator replaces each adapter's independent queue/lifecycle policy | 25–35 | 5–8 weeks, staged; adapter semantics and ambiguous delivery differ | Extract incrementally after the ledger boundary |
| 3 | Canonical conversation/tool model replaces repeated provider-shape interpretation and lossy reducers | 35–45 | 3–5 weeks; old history and provider-specific details must survive | Do now, beginning with results and errors |
| 4 | Shared query and mutation ownership replaces component-local fetch effects and competing caches | 35–45 | 3–5 weeks; duplicate cache authorities and incorrect keys | Do now for files, Git, session lists and pickers |
| 5 | Structured repository/file contracts replace app-side Git text parsing and reconstructed paths | 25–35 | 2–3 weeks; daemon/app rollout and unusual filenames | Do now; a particularly bounded migration |
| 6 | Lifecycle-owned tasks and I/O replace scattered timers, subprocess/listener cleanup and unbounded writers | 15–25 | 2–4 weeks; cancellation cannot undo completed side effects | Introduce shared primitives as these families are fixed |
| 7 | Bounded parsing/rendering pipeline replaces unrestricted regex and diff work on the UI thread | 8–12 | 1–2 weeks for limits/fallbacks; wider grammar replacement costs more | Add budgets now; migrate grammars selectively |
| 8 | Structured Claude runtime replaces pane text as execution and input authority | About 6 direct pane findings; other benefits overlap ranks 2/6 | 1–2 week feasibility spike, then perhaps 6–10 weeks; terminal parity is uncertain | Spike now; defer wholesale replacement |

**1. Make durable acceptance a transaction, and retain identity after delivery.**

Replace `domain/queueStore.ts`, `domain/receipts.ts`, the adapter inbound/checkpoint files, `relay/outboundSpool.ts`, and the execution-relevant part of window records with a small daemon database. SQLite is a reasonable local choice. The value is a transactional API such as accept command, record dispatch attempt, record runtime observation, and acknowledge outbound event. Callers should receive a durable acceptance result only after its transaction commits; they should not choose whether `requireDurable` matters.

The motivating findings are “Local send acknowledges prompts after queue persistence fails,” “Handoff jobs acknowledge prompts without requiring durable queue storage,” “A failed queue update destroys previously acknowledged prompts,” and the lost/debounced receipt cases. The current stores have different failure contracts: some return false, some swallow errors, some rewrite the live file, and others rename a whole-array snapshot. The recent ownership-only spool repairs show the deeper problem: queue state, delivery identity and recovery checkpoints are being transferred between files without a transaction. A confirmed sequence belongs in a retained receipt table, even after the pending queue row disappears.

Keep command ID, payload version, session generation, runtime attempt ID and event sequence distinct. Commit the observation, its durable output and the corresponding local checkpoint together. Keep remote acknowledgement separate. A known terminal outcome must be saved immediately; its outgoing position can remain after that session's preceding output. A single outbox scheduler then sends persisted sequence order and retries by stable event ID. This removes the need for several partially overlapping replay chains and memory flags to represent whether a record is merely scheduled, persisted, or remotely accepted.

This does not make agent execution exactly once. Codex client IDs are correlation IDs in the reproduced cases. A crash after sending but before receiving evidence still needs an explicit unknown outcome and reconciliation before any resend. Likewise, SQLite alone does not choose correct transaction boundaries. Use the intended durability setting: WAL with `synchronous=FULL` synchronizes commits for power-loss durability, unlike WAL/NORMAL's weaker guarantee. Keep transactions short and include WAL-aware backup and recovery procedures. [SQLite documents these distinctions](https://www.sqlite.org/wal.html).

Do not replace the relay's existing transactional core just to standardize database products. Fix its exclusive data-directory ownership: the audit's simultaneous PGlite opener case loses committed writes despite transaction use inside each process. A separate Postgres server becomes appropriate when multiple relay processes are an actual deployment requirement. Database capacity also remains finite: bound pending bytes, refuse new work before storage becomes unusable, and define retention by durable acknowledgements rather than evicting live obligations. User-file and configuration saves still need atomic file replacement; moving command state into a database does not protect arbitrary working-tree writes.

I would start with queue acceptance plus receipts/outbound records. Import old files once behind a versioned migration, preserve them for inspection, and switch each session to one authoritative writer. Avoid indefinite dual writing. This is the largest risk reduction even though it is not the largest raw finding count.

**2. Put execution policy in one daemon session coordinator.**

I would make the queue coordinator-owned, but would not put every local session inside the relay polling loop. CLI sends, handoffs and local terminal activity exist without a relay offer. Extract a daemon `SessionCoordinator`; let `nucleusLane` translate relay offers into its operations. Claude, Codex, OpenCode, Pi and Agy become runtime drivers that submit, interrupt, observe and reconcile. A driver may need protocol buffering, but it should not own another independently authoritative work queue.

The coordinator owns a generation for every session replacement and an attempt identity for every submission. Its commands transition durable state through queued, submitting, accepted/unknown, running and terminal outcomes. Cancellation is a durable requested transition, with interruption attempted until confirmed or explicitly unresolved. An idle runtime is evidence that execution stopped, not evidence of success. The findings “Failed agent turns are terminalized as completed,” “A failed old dispatch overwrites the replacement queue after restart,” “Cancelling OpenCode before admission leaves the prompt runnable,” and “A fast Codex completion restores a finished turn as active” become violations of one contract rather than separate adapter conventions.

Serialize short state transitions, not whole network operations. Record an operation token, release the coordinator, perform I/O, and apply its result only if the token and generation still own the state. Holding a session lock through a slow submit, archive or callback into create/restart would recreate the self-join deadlocks already found. Reorder and queued-only deletion also need their preconditions checked in the relay transaction that changes delivery state; a daemon actor cannot make those relay operations atomic remotely.

Retain capability differences. OpenCode steering into an existing turn, a Claude terminal draft, and a Codex ambiguous submission cannot be flattened into one “busy” boolean. Independently started terminal turns must be observed with their own provenance. Recovery must preserve exact runtime/session identity instead of searching for a plausible transcript. Port one adapter and the local-send path first, replay the existing failure-order harnesses against the contract, then migrate the remaining drivers. I would do this now as extraction, not as a simultaneous rewrite of every adapter.

**3. Normalize a conversation once; make tool views presentation-only.**

Introduce a versioned canonical model at adapter ingestion and the app's legacy-record boundary. A tool invocation should have a stable owning session/turn/call identity, validated arguments, an explicit outcome, ordered result blocks, and optional structured command or file-change data. Preserve unknown raw data for a safe fallback. Distinguish failed, cancelled, denied and successful outcomes; preserve valid zero, false and empty results. Every compact view, full view, group summary and badge should consume the same normalized result.

The useful boundary is larger than the grouping's seven “tool view field mapping” entries. The audit includes structured Bash failures reported as empty completion, Codex failed patches displayed as successful edits, null argument crashes, list-form patches losing renames, Task details dropping the answer, and multi-block results losing everything after their first text block. Fixing twenty view components separately leaves multiple interpretations of the same outcome. Start with one result/error presenter and normalized command/file-change models, retaining specialized presentation only where it adds information.

Also replace the order-sensitive part of the reducer with an identity-based projection. Persist or retain an unmatched result until its call arrives; key subagent children by call identity; merge duplicate live/history observations idempotently. Historical lifecycle events must update historical state without overwriting the current snapshot. “Tool results loaded before their calls are permanently discarded,” “Parallel Task calls … misattribute their subagent output,” and the old-reset/current-state failures require this projection work, not merely better view props. Do not run the entire historical log again on every render: use indexed entities and rebuildable, versioned projections.

This costs more than a new TypeScript union. Each provider and historical shape needs a translator, and validation must isolate a malformed item rather than discard an entire page. Keep captured provider fixtures and assert equivalent live/replayed projections, reordered call/result arrival, and identical compact/full outcomes. I would ship the result/error contract first, then the projection migration. I would not alter decision enforcement as part of this presentation/model change.

**4. Give fetched resources and user mutations stable owners outside components.**

Use one resource query layer for Git status, file contents, session lists, history discovery and other machine reads. TanStack Query is a sensible implementation candidate; alternatively, enforce the same contract in a smaller existing service. The key must include the actual resource identity: machine, repository/session, path, operation options and relevant version. A request writes only its resource cache, never whichever component happens to be mounted when it finishes. Error, authoritative empty result, unavailable context and last successful data remain separate states.

This directly addresses the stale machine/project picker results, file loads overwriting another file after hashing, older polls replacing newer contents, failed refreshes erasing cached lists, prefetches overwriting saves, and stopped synchronizers repopulating replacement caches. It also replaces `ValueSync` retrying an obsolete rejected value forever. Focus, reconnect and invalidation become explicit resource policies, with coalescing and bounded retries. TanStack Query exposes cancellation signals, but unused queries are not automatically cancelled unless the signal is consumed; installing the library alone does not fix stale writes. Native app focus and navigation screen focus also need explicit integration. [Cancellation contract](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation), [native focus integration](https://tanstack.com/query/latest/docs/framework/react/react-native).

A query cache is not the owner of unsent user intent. Keep draft versions, attachments, pending saves and send attempts in session/resource-scoped state that survives remount. An acknowledgement updates the attempt it names; it must not clear a newer composition or infer abandonment from another send's success. Persist sends that must survive application restart. HTTP cancellation cannot retract a command already accepted remotely. A mutation layer should validate the domain result, return an operation outcome, and apply optimistic changes and rollback only to the version it owns.

Do not move the conversation reducer into a generic query cache as part of this. Its cursor and projection rules belong to rank 3. Similarly, Git status/line counts are not a content version: the query layer still needs an actual revision or explicit invalidation when same-sized content changes. Migrate the file/Git cluster first, remove its duplicate Zustand/cache writers, then migrate the lists and pickers. This is worthwhile now; migrating every screen at once would make mixed ownership worse temporarily.

**5. Finish moving repository interpretation to a structured daemon service.**

The daemon already returns parsed status entries, but `gitStatusFiles.ts` and `gitStatusSync.ts` still separately request and parse textual numstat, use empty strings for failed reads, and retain older porcelain parsers. Establish one versioned repository response containing repository root, session-relative relationship, branch/detached/unborn state, exact path identities, index/worktree/conflict status, rename source/destination, binary status and explicit available/unavailable line counts. Return raw file bytes separately from display decoding. The app should display these facts without reconstructing filenames or inferring successful reads from empty text.

This targets the quoted/trailing-whitespace/pipe/prototype filenames, rename expressions, binary counts, AA/DD conflicts, linked worktrees, unborn HEAD and subdirectory-root inconsistencies. Parse Git's machine formats once at the daemon boundary: status porcelain v2 with NUL delimiters, NUL-delimited numstat including its two-path rename form, and structured ref enumeration. Git documents the exact [status pathname format](https://git-scm.com/docs/git-status) and [numstat/NUL representation](https://git-scm.com/docs/git-diff). `-z` is necessary but does not make a naive split correct for every record type.

A cross-platform path contract should separate display text from the identifier sent back to file operations. In particular, a tracked symlink's name is not interchangeable with its resolved target, and repository-relative paths are not session-relative paths. Decide how unsupported filename byte sequences are represented; blindly decoding every pathname as UTF-8 is not a lossless identity. External filesystem changes can still race several Git commands, so report a snapshot/revision policy or retry detected changes rather than promising atomicity that Git does not provide.

I would implement this now and remove obsolete parsing consumers after a compatible rollout. Keep the system Git binary initially; adopting a new Git engine would add behavioral differences without being necessary for this boundary. Some old-parser audit findings may already be unreachable on the current path; deleting those paths prevents recurrence but is not the same as fixing an active user failure.

**6. Make asynchronous work and resources belong to a lifecycle.**

Provide a small task scope for a session generation, connection or resource. It owns child processes, timers, subscriptions and cancellation; every spawned task has a result/error policy. Disposing the scope prevents later callbacks from updating its successor and cleans up resources when they actually finish. Build shared bounded subprocess and stream helpers on this: deadlines, complete frame identities, streaming text decoding, byte limits, and drain-aware writes. A timeout must stop or fence the underlying operation; racing an uncancellable promise against a timer is insufficient.

This targets late Codex connections, late OpenCode startup, tmux's unhandled spawn-error-after-stop case, transcript watcher replacement/descriptor leaks, UTF-8 split chunks, stalled synchronous tmux calls, and slow event clients growing response buffers. Lifecycle cancellation must preserve enough error listeners to absorb a child's eventual failure. Process shutdown must track the process group and surviving children, not just the launcher PID. EOF/stream close and process exit are different events; Agy advancing before stdout closes illustrates why.

The helper does not know whether retrying a submit is safe, and it cannot reverse a completed file write. Those decisions stay with ranks 1/2. Nor does an AbortController fix every native SDK state transition or every modal bug. I would introduce these primitives while fixing the I/O families, migrate subprocess/stream consumers first, and avoid a universal “async framework” that hides errors or retries all operations automatically.

**7. Bound expensive parsing as a product contract.**

Several unrelated utilities can monopolize the same UI thread: syntax highlighting, malformed Markdown brackets, unfinished Joy tags, path-like token searches, tool-error parsing and diff pairing. Put size, depth and work limits at the rendering boundary. Above the budget, render a safe plain-text or whole-line fallback and allow explicit expansion. Run expensive optional analysis in a cancellable worker where the platform supports it; use bounded fallback paths on native. Bound output allocation as well as input length.

This would prevent roughly 8–12 stall/resource failures, including cases outside the grouping's six parse-freeze entries. It would not repair all Markdown, CSV or path semantics. Replace handwritten grammar fragments with a tested grammar implementation where useful, and recognize Joy extensions only in the appropriate parsed context so examples inside code remain literal. I would add the limits now, then continue correctness fixes by parser family. Building a new universal parser is unjustified; moving an unbounded parser to a worker merely relocates its resource leak unless work and cancellation are bounded too.

**8. Explore a structured Claude runtime, but price the terminal requirement honestly.**

Pane text should eventually be a display and diagnostic channel. It currently determines whether input is empty, work is active and a mode is current. The audit's six direct cases include typed `Try "…"` mistaken for a placeholder, numbered drafts mistaken for selectors, footer words inside draft text, old reply text mistaken for the active status, and duplicate draft restoration. More regex patches cannot make arbitrary conversation text a reliable control protocol.

For daemon-managed sessions, prototype a long-lived structured runtime that accepts identified input and emits submission, tool, turn and interruption observations. The Claude Agent SDK documents long-lived streaming input, multiple messages and interruption, so it is a credible candidate for a prototype. That documentation does not establish that it can transparently attach to an arbitrary existing interactive Claude TUI or preserve Joy's terminal workflows. [Streaming-input documentation](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode).

The unresolved product question is whether users must keep independently typing into that same terminal, with all existing slash commands, draft preservation, resume behavior and background tasks. If yes, require a supported structured control channel for that process or build a Joy-owned terminal client over the managed runtime. Hooks and transcript events can reduce guessing in the meantime, but do not expose every live editor state. Treat uncertain pane evidence as unknown, and retain the bounded liveness fallback; do not launch a second runtime against the same conversation to obtain better telemetry.

I would fund a short spike with explicit parity checks and a stop decision. I would keep repairing the pane family until it proves command identity, input arbitration, interruption, session recovery and terminal parity. Six direct findings alone do not justify a rushed backend replacement. Its longer-term value is removing a fragile dependency on another application's visual layout.

I would ship this as a sequence of narrow migrations: durable acceptance and retained receipts first; a normalized tool-result presenter and structured Git endpoint as independent app-visible improvements; then the session coordinator and resource-query migrations. Each slice should delete an old authority. Useful exit checks are crash recovery at each persistence boundary, late callbacks after replacement, lost acknowledgements followed by retry, and equivalent conversation projection under reordered history/live events. The existing review harnesses are valuable starting fixtures for those contracts.

Keep fixing the isolated families while this proceeds. Platform labels, touch/keyboard behavior, clipboard acknowledgements, fixture mistakes, semantic-version parsing and small presentation defects do not need a new architecture. I would not introduce microservices, a distributed workflow system, a new Git implementation or full event sourcing for every preference. The practical investment is a few authoritative contracts with visible failure states, plus removal of the duplicate implementations that currently disagree about them.
